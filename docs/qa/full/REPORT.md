**QA agent:** qa-full (independent, no code changes made)
**Date:** 2026-09-05
**Build tested:** `npm run build` (production Turbopack build) + `npm run start -p 3500`, `npm run worker` in the background (ffmpeg 9.0.1 on PATH, sidecar not started — worker fell back to local `arnndn` denoise per `docs/AUDIO_ARCHITECTURE.md`). Re-verify anything touching Enhance/Review/Duet-record after those changes land.
**Accounts used:** two throwaway Supabase accounts created via the documented admin-API pattern (`e2e+qafulla-*@akinti.test`, `e2e+qafullb-*@akinti.test`), onboarded through the real `/onboarding` UI. Real signup form was also exercised directly and correctly hit Supabase's documented email rate limit ("Too many emails requested. Wait a few minutes and try again.") — expected, not a defect.

## Overall score: 6 / 10

Visual/interaction craft is genuinely high — onboarding, the waterline system, Duet chains, challenges, structured feedback, notifications and the persistent player all match DESIGN.md/SCREENS.md closely and mostly pass axe with zero serious/critical violations. But two P0s break named, core-loop functionality (a user cannot start a new conversation with anyone, at all; the audio pipeline can crash and leak a raw ffmpeg stack trace onto a published Wave's page), performance misses every stated mobile budget by a wide margin on all four routes tested, and one systemic color-contrast token fails WCAG AA across roughly 43 files. "Works on paper" is not met yet.

Two items were investigated and retracted as false alarms, documented here for transparency and not counted above. First: the Settings "Delete account" control is not on /settings/account — it is correctly on the /settings hub per SCREENS.md section 11, exactly where the code puts it, and the full flow (copy, type-to-confirm, Escape-to-close with a roughly 600ms sheet transition, and focus returning to the trigger button) all work correctly. Second: document.querySelectorAll('audio').length reads 0 during active playback everywhere, by design — playbackStore.ts creates a single document.createElement("audio") element that is deliberately never inserted into the DOM tree, so the literal query specified in the QA brief cannot observe it. Singularity was verified instead via network trace (exactly one signed-URL round trip per Play tap) and via the persistent player strip, which does correctly follow real Link client-side navigation on both breakpoints (see below); it only fails to appear after a hard page reload via goto, which is expected SPA behavior, not a bug.

## Golden path (steps 1-2 of the brief): console/network summary

Full sweep across roughly 25 authenticated screens (Explore, Search, both profiles, Followers/Following, Messages list, all 8 Settings sub-pages plus 4 Content sub-pages, Analytics, Challenges hub and slug, Hashtag): 0 console errors, 0 failed (4xx/5xx) network requests. The only "failures" seen in raw Playwright event logs across the whole run were net::ERR_ABORTED on Next.js's own RSC prefetch requests, which is expected browser behavior when a prefetch is superseded by a real navigation before it finishes — not counted as defects. The one genuine, reproducible request-level failure in the entire run is defect 1 (a clean application-level rejection with no HTTP error, since it is a server-action result, not a route response).

## Not fully tested, known gaps in this pass

Voice message send/receive and the message thread page at /messages/[id] were blocked entirely by defect 1; there is no way to reach a real conversation between two accounts that have not spoken before on this project. Real native-microphone constraint verification (confirming echoCancellation, noiseSuppression and autoGainControl are actually false at the getUserMedia call) was not done, since the fake Chromium device does not expose the constraints object it was called with from the outside, and the code path was not separately unit-audited in this pass. The PWA install flow, offline behavior, Media Session lock-screen controls, and visualViewport keyboard avoidance were not exercised. Reduced motion was only checked on one Wave-page screenshot (docs/qa/full/shots/03-reduced-motion-wave-page.png); no systematic per-screen reduced-motion diff was performed.
