# AKINTI — internationalization (i18n)

Turkish-first, English-second. This document is the source of truth for how
locale is resolved, where translated copy lives, which product terms
deliberately do not translate, and — most importantly — what is migrated to
this system today versus what is still English-only hardcoded copy.

**Server-side status: complete.** Every Server Action's `formError`/
`message`/`fieldErrors` string, every Zod validation message, every push
notification, and the config-constant labels named in this stage's brief
(enhancement presets, creation-type labels, processing-error copy) resolve
per request/recipient locale — see §8 for the pattern and §9 for how to add
a new one. `scripts/i18n-check.ts` enforces this with a zero-tolerance scan
(no ratchet, no baseline) over `src/app/**/actions.ts`, `src/lib/moderation`,
`src/lib/validation`, `src/lib/push` and `src/config` — any new hardcoded
string in those surfaces fails `npm run lint` immediately. Client-side
screen-by-screen extraction (the `.tsx` ratchet in §3 below) is separate,
ongoing work owned by other stages.

## 1. Library and architecture

`next-intl` (`docs/research/libraries.md` has no prior i18n decision; this
is the one made for this stage, consulted against the Next 16 App Router
docs via Context7 before wiring). No URL locale prefixes — this product
never shows `/tr/...` or `/en/...`; locale is resolved server-side, per
request, from:

1. `profiles.locale` (migration `20260906130000_profile_locale.sql`) — the
   signed-in user's own choice, if they have made one.
2. The `akinti_locale` cookie (`src/i18n/locale.ts`'s `LOCALE_COOKIE`) —
   works signed out too, and is the fast path immediately after a language
   switch.
3. `Accept-Language` — Turkish for a Turkish browser, English otherwise.
4. Default: English (`DEFAULT_LOCALE` in `src/i18n/locale.ts`).

The precedence itself is a pure function, `resolveLocale()`
(`src/i18n/locale.ts`), unit-tested in `src/i18n/locale.test.ts` — the actual
cookie/header/profile reads live in `src/i18n/request.ts` (next-intl's
`getRequestConfig`), which is otherwise untestable without a request
context.

`<html lang>` and page metadata (`src/app/layout.tsx`'s `generateMetadata`)
resolve the same way, so a Turkish visitor gets `lang="tr"` and a Turkish
`<title>`/`<meta description>` together, not just translated body copy.

## 2. Where translated copy lives

- `src/messages/en.json` / `src/messages/tr.json` — namespaced per
  screen/component (`Metadata`, `Manifest`, `Offline`, `Flow`, `Settings`,
  `Terms`). `en.json` is the typed source (`src/i18n/global.ts` registers it
  against next-intl's `AppConfig`), so a typo'd or missing key is a
  TypeScript error at the call site, not a silently blank string. `tr.json`
  must carry the exact same key set — enforced by `scripts/i18n-check.ts`'s
  key-set diff (no baseline, zero-tolerance), which fails `npm run lint` the
  moment a key is added to one file without the other (review3 finding 26).
- `src/config/terminology.ts`'s `TERMS` — **still English-only**, and stays
  that way for now. See §4.

## 3. What is actually migrated

Wired end-to-end (cookie + profile write, `<html lang>`, translated render,
verified in both locales via `npm run typecheck && npm run lint && npm run
test && npm run build`):

- Root `<html lang>` and page `<title>`/`<meta description>`
  (`src/app/layout.tsx`).
- The PWA manifest name/short name/description and `lang`
  (`src/app/manifest.ts`).
- The `(auth)` layout's tagline (`src/app/(auth)/layout.tsx`).
- The offline fallback page (`src/app/~offline/page.tsx`).
- Flow's empty/error state and its page-level fallback error string
  (`src/components/flow/FlowEmptyState.tsx`, `src/app/(app)/flow/page.tsx`),
  and Flow's page title.
- Settings → a new language row (`src/components/settings/LanguageSwitchRow.tsx`)
  that writes both the `akinti_locale` cookie and, when signed in,
  `profiles.locale`.
- The full `Terms` namespace (mirroring every `TERMS` key 1:1, hand-written
  Turkish) — available for any future call site to adopt, not yet wired
  into the ~150 places that still import the static `TERMS` object.
- **Every Server Action** (`src/app/**/actions.ts`): every `formError`,
  `message` and `fieldErrors` value resolves via `getTranslations()`/
  `useTranslations` for the request's locale (see §8). Zod validation
  messages across `src/lib/validation/**` and the rate-limit/moderation
  copy in `src/lib/moderation/errors.ts` are included.
- **Push notifications** (`src/lib/push/send.ts`): title/body resolve
  against the *recipient's* own `profiles.locale` (falling back to
  Turkish), never the actor's request locale — see §8.3.
- **Config-constant labels**: `ENHANCEMENT_PRESETS`/`PRO_ENHANCEMENT_PRESETS`
  names and descriptions (`src/lib/audio/enhancement.ts`), `CREATION_TYPES`
  labels (`src/config/terminology.ts`, resolved via the existing
  `Terms.recorded`/`uploaded`/`duet` keys), `getProcessingErrorMessage`'s
  copy, `DUET_MODE_DESCRIPTION` and `PRO_INCLUDE_KEYS` all render through a
  translated parallel namespace at every call site — the English-only
  constant itself is unchanged (§4's reasoning), only what gets rendered.

**Client-side `.tsx` copy not yet migrated**: `scripts/i18n-check.ts`'s
original scan (JSX text and the conventional text attributes —
`title`/`label`/`description`/`placeholder`/`alt`/`aria-label`/
`aria-description` — across `src/app/**`/`src/components/**`) is a baseline
ratchet in `scripts/i18n-check.baseline.json`: `npm run lint` fails if a
file's hardcoded-copy count grows past its baseline entry, or if a
brand-new file introduces hardcoded copy with no baseline entry at all, but
does not fail on already-baselined debt. This has shrunk considerably across
several stages (137 files/615 instances at one earlier point down to 7
files/17 instances at the time of writing — `moderation/page.tsx`,
`search/page.tsx`, `suspended/page.tsx`, `error.tsx` and a handful of
others); check `scripts/i18n-check.baseline.json` directly for the current,
exact list rather than trusting a number here to stay fresh. The path to
closing what remains: pick one baseline file at a time, move its strings
into a `messages/{tr,en}.json` namespace, translate by hand, then run
`npx tsx scripts/i18n-check.ts --update-baseline` to shrink the baseline to
match.

The **server-side** surfaces this ratchet never covered at all —
`formError`/`message`/`fieldErrors` in Server Actions, Zod validation
messages, push notification copy, and the config-constant labels named
above — are the ones this stage (i18n-c) closed completely, and are held to
zero via a separate, non-ratcheted scan (§1's status note, §8).

## 4. Why `TERMS` did not move

`src/config/terminology.ts`'s `TERMS` is imported as a plain compile-time
constant by roughly 150 files, several as `export const metadata = { title:
TERMS.x }` — a static object literal evaluated once at module load, before
any request (and therefore before any per-request locale) exists. Rewriring
every one of those call sites to a translated, request-scoped equivalent
(`useTranslations`/`getTranslations`, or converting a static `metadata`
export to `generateMetadata`, as this stage did for the root layout and
Flow) is a large, mechanical migration in its own right, file by file, each
one needing a real look rather than a find-and-replace. Out of scope for
this stage to do safely across the whole codebase in one pass. `TERMS`
therefore stays as the English original; `messages/{tr,en}.json`'s `Terms`
namespace is the translated parallel, ready for whichever stage next
touches a given screen to adopt.

## 5. Turkish copy quality and collisions

Sentence case, no exclamation marks, no em dash, never uppercase Turkish
(İ/ı is casing-dependent), matching `docs/design/DESIGN.md` §3. Several
English source terms are overloaded across more than one Turkish word;
resolved explicitly below rather than machine-translated 1:1.

| English | Context | Turkish | Why |
|---|---|---|---|
| Wave / Duet | Product noun (brand term) | **Wave** / **Duet**, unchanged | Coined product nouns, not generic English words — translating them would be like translating "Tweet." Plural takes a Turkish apostrophe-suffix: Wave'ler, Duet'ler. |
| Atışma / Cypher / Layer | Duet modes | Unchanged | Named modes (`docs/PRODUCT_V2.md`), not descriptions — Atışma is already a Turkish word (a traditional call-and-response verse duel), and Cypher/Layer are established genre/production terms even in Turkish music culture. |
| Save (bookmark a Wave, or save a form) | Verb/button | **Kaydet** | One consistent verb for both "save this Wave" and "save these settings." |
| Record (start recording) | Button | **Kaydı başlat** | "Kaydet" was already taken by Save above; a plain "Kaydet" button for recording would collide with every Save button in the product. "Kaydı başlat" (start the recording) reads as a distinct action. |
| Recorded (creation-type tag) | Noun/tag | **Kayıt** | The noun form of "recording," used as a short filter-chip label, parallel to Uploaded → **Yükleme**. |
| Replay | Metric/action | **Tekrar** | Not "yeniden oynat" (too long for a metric label) and not "tekrar oynatma" (redundant with the Play metric next to it). |
| Play / Plays (metric) | Count noun | **Oynanma** | Distinct from the transport **Oynat**/**Duraklat** (Play/Pause) verbs — "Oynanma" (times played) versus "Oynat" (the button). Reusing one Turkish word for both would read as a typo next to a number. |
| Comment (as a metric) | Count noun | **Yorum** | If a future screen adds a distinct "write a comment" action button (not currently a separate `TERMS` key), it should read "Yorum yap," not reuse this noun form. |
| Flow | Nav item / feature name | **Akış** | Unlike Wave/Duet, "Flow" is a plain English word here, not a coined brand term, so it translates. Distinct from AKINTI itself (which also evokes "current/flow" in Turkish) — the two are related in imagery but are not the same string anywhere in the product. |
| Follow / Followers / Following | Social graph | **Takip et** / **Takipçiler** / **Takip edilenler** | Standard Turkish social-app vocabulary (matches Instagram/Twitter's Turkish localizations, which readers already know). |
| Challenge | Themed prompt/contest | **Meydan okuma** | The same term Duolingo and other Turkish-localized apps use for "challenge" — reads naturally, not a literal dictionary translation. |
| Onboarding CTA ("Get started") | Button | **Başlayalım** | "Hadi başlayalım" felt too casual/exclamatory for the no-exclamation-marks rule; "Başlayalım" (let's begin) keeps the warmth without punctuation. |

Known imperfection, not fixed in this pass: Turkish nouns do not take a
plural suffix when preceded by a count ("3 oynanma," not "3 oynanmalar"),
but `TERMS`/`Terms`' `singular`/`plural` pairs (e.g. `play`/`plays`,
`share`/`shares`) are reused for both a bare metric context and a
non-counted list-header context in English. The `Terms` namespace picks one
Turkish form per key rather than branching on context, which means a
metric row rendered directly from `Terms.shares` may read grammatically
looser in Turkish than in English until that call site moves to a proper
ICU plural message. Documented here rather than silently accepted.

## 6. Formatting

`useFormatter`/`getFormatter` (next-intl, backed by `Intl`) for anything
locale-sensitive — never hand-rolled: relative time ("3 dk önce" / "3 min
ago"), counts (Turkish nouns do not pluralize after a number; see above),
and prices. `src/i18n/formats.ts` defines named formats for TRY and USD
currency display — currency is a formatting parameter passed explicitly by
the caller (`{style: "currency", currency: "TRY"}`), not implied by the
active UI locale, since AKINTI Pro pricing is currency-scoped to the
account/region, not to which language the UI happens to be showing.

## 8. Server-side pattern (Server Actions, Zod validation, push, config)

The server has no `NextIntlClientProvider`/render-scoped context the way a
Client Component does, but it does have one thing a background job never
does: a real, ambient request. `getRequestConfig` (`src/i18n/request.ts`)
already resolves that request's locale on every call; a Server Action
(and any Server Component) calls `getTranslations()` and gets a translator
scoped to that same resolved locale, no different from how a page calls it
for its own copy.

### 8.1 Server Action messages

Every action module imports `getTranslations` from `next-intl/server` and
resolves either a **namespaced** translator (`getTranslations("SomeNamespace")`,
when every message it needs lives in one namespace) or a **root** translator
(`getTranslations()`, no argument) when it needs to reach across namespaces
— most commonly the shared `Common` namespace (`Common.notConnected`,
`Common.signInToDoThat`, `Common.rateLimited`, `Common.recordingNotFound`,
`Common.noPermission`, `Common.sessionExpired`, `Common.usernameTaken`,
`Common.couldNotDoThat`, `Common.waveNotAvailable`, `Common.unblockFailed`,
`Common.accountUnblocked`, `Common.somethingWentWrong`) alongside its own
domain namespace (`SettingsActions`, `ChallengesActions`, `CreateActions`,
`MessagesActions`, `ModerationActions`, `ProfileActions`, `WaveActions`,
`DuetsActions`, `DuetRecordActions`, `AuthActions`, `OnboardingActions`, and
so on — one namespace per action module, named after the module).
A root translator is required, specifically, wherever a shared helper
function (an action's own `describeError`, or `mapModerationError` in
`src/lib/moderation/errors.ts`) needs to resolve a key from a namespace
other than its caller's — `t("Common.rateLimited")` only resolves correctly
against a root-scoped `t`.

**Why a plain `MessageTranslator` type, not next-intl's real `Translator`
type, on these shared helpers**: typing `describeError`/`mapModerationError`/
`translateFieldErrors`/`translateValidationMessage`'s `t` parameter as the
real, strictly-keyed translator forces TypeScript to compute
`NamespacedMessageKeys` across the *entire* app's message tree at every one
of these ~50 call sites, which hits a real complexity ceiling ("union type
too complex to represent" — `tsc` error `TS2590`) once a message file grows
this large. `src/lib/validation/translate.ts` exports a loose
`MessageTranslator = (key: string, values?: Record<string, unknown>) =>
string` instead; a local `const t = (await getTranslations()) as
MessageTranslator;` (or a namespaced equivalent) is the one place per
function that bridges the gap. A direct call like `t("SettingsActions.
saveFailed")` right after that still reads and behaves identically —
only the *static* "is this really a valid key" check is gone for a
root-scoped `t`, caught instead by this file's own tests and
`scripts/i18n-check.ts`'s server-surface scan (§9 step 4).

### 8.2 Zod validation messages

Every custom message in `src/lib/validation/**` is written as a
`"namespace.key"` string (the `validation` namespace, lowercase, e.g.
`.min(3, "validation.usernameMin")`) instead of a hardcoded English
sentence, because a Zod schema is a plain module-level constant evaluated
once at import time — before any per-request locale exists, the same
reasoning §4 gives for why `TERMS` stays English-only. The one message that
needs an interpolated value (`validation.duetTooManyTurns`,
`src/lib/validation/duets.ts`) is written `"validation.duetTooManyTurns:12"`
— everything after the first `:` becomes the `{value}` placeholder.

`src/lib/validation/translate.ts` turns a raw Zod issue message into real
copy at the Server Action boundary:

- `translateFieldErrors(t, fieldErrors)` — pass a Zod `safeParse` failure's
  `.error.flatten().fieldErrors` through this *before* `fieldErrorsFromZod`
  (`src/lib/auth/types.ts`) collapses it to one message per field; it never
  changes that collapsing step.
- `translateValidationMessage(t, message)` — for the single-message case
  (`parsed.error.issues[0]?.message`), used directly in every action that
  returns a bare `{ ok: false, error: string }` rather than `fieldErrors`.

Both pass a message that doesn't look like `"namespace.key"` (a Zod default
like `"Invalid input"`, or an arbitrary caught error's `.message` used as a
`superRefine` fallback) straight through, untranslated — this module never
invents a translation for a key it doesn't recognise, and never throws.

### 8.3 Push notifications

`src/lib/push/send.ts`'s `sendPushToUser`/`notifyDuetPush` take message
**keys** (`titleKey`, `bodyKey`, `titleParams`/`bodyParams`), never a
resolved string — the recipient of a push is, by definition, never the
actor whose request triggered it, so there is no ambient request locale to
read the way a Server Action's own response has. `send.ts` resolves the
*recipient's* `profiles.locale` itself (falling back to Turkish, this
product's primary language, when unset — not `DEFAULT_LOCALE`/English) and
looks the key up directly against `src/messages/{tr,en}.json` via a small
hand-rolled resolver (`src/lib/push/messages.ts`) — deliberately not
next-intl's `createTranslator`, since a push title/body only ever needs a
plain `{name}` placeholder, never ICU plurals/dates.

Every `titleParams`/`bodyParams` value is itself a `Terms.*` key (e.g.
`{ duet: "duet", wave: "wave" }`), not a literal display string — `TERMS.x`
(`src/config/terminology.ts`) is deliberately English-only, so interpolating
a raw `TERMS.duet` value into an otherwise-Turkish push body would embed
English mid-sentence. `resolvePushMessage` resolves each term key against
the *same* locale as the surrounding message before interpolating.

### 8.4 Config-constant labels

`ENHANCEMENT_PRESETS`/`PRO_ENHANCEMENT_PRESETS` (`src/lib/audio/
enhancement.ts`), `CREATION_TYPES` (`src/config/terminology.ts`),
`getProcessingErrorMessage`'s code map, and `DUET_MODE_LABEL`/
`DUET_MODE_DESCRIPTION` are all plain module-level constants for the same
reason `TERMS` is (§4) — evaluated once, before any locale exists. None of
them are rewritten; each gets a translated parallel instead, resolved at
the render site:

- A small `as const satisfies Record<Id, { label: string; description:
  string }>` map from id → message key, defined next to the component that
  renders it (`EnhancementPicker.tsx`'s `PRESET_MESSAGE_KEY`,
  `EnhanceStage.tsx`'s `PRO_PRESET_MESSAGE_KEY`, `DuetModePicker.tsx`'s
  `MODE_DESCRIPTION_KEY` — the original precedent for this pattern). The
  `as const satisfies` combination matters: a plain `: Record<Id, ...>` type
  annotation widens every value to `string`, which fails the same strict
  `NamespacedMessageKeys` check §8.1 describes for a *namespaced* (not root)
  translator too.
- `CREATION_TYPES[x].label` specifically needed no new map at all — every
  creation type id (`recorded`/`uploaded`/`duet`) is already a real key
  under the existing `Terms` namespace, so call sites just moved from
  `creationType.label` to `tTerms(creationType.id)`.
- `getProcessingErrorMessage`'s three codes moved to a `ProcessingErrors`
  namespace, resolved by `ProcessingBanner.tsx` at render — the exported
  function in `terminology.ts` itself is untouched (an existing test asserts
  its English default map directly), so this is a render-site translation,
  not a signature change.

## 9. How to add a new server-side string

1. Pick (or create) a namespace in `src/messages/en.json` — one action
   module's own namespace (named after the file, e.g. `ChallengesActions`)
   for a message only that module uses, `Common` for one several modules
   already share, `validation` for a Zod schema message, or a
   component-adjacent namespace for a config-constant label.
2. Add the same key to `src/messages/tr.json` with real, reviewed Turkish
   (sentence case, no exclamation marks, no em dash, no uppercase Turkish —
   `docs/design/DESIGN.md` §3, §5 above) — `en.json`'s keys are the typed
   source (`src/i18n/global.ts`), so a key present in one file but not the
   other is a silent gap, not a type error.
3. Call it:
   - Server Action: `const t = await getTranslations("YourNamespace");` (or
     `getTranslations()` + a full `"YourNamespace.key"` path, only when you
     also need a key from a *different* namespace in the same function —
     see §8.1's `MessageTranslator` note if you're passing `t` into a shared
     helper).
   - Zod schema: `.min(1, "validation.yourNewKey")` — never a literal
     English string; see §8.2 for the `:param` interpolation syntax if the
     message needs one.
   - Push notification: pass `titleKey`/`bodyKey` (+ `titleParams`/
     `bodyParams`, each value a `Terms.*` key if it's a product term) to
     `sendPushToUser`/`notifyDuetPush` — never a resolved string.
   - Config-constant label: add an entry to the id → key map next to the
     rendering component (§8.4), not to the constant itself.
4. Run `npx tsx scripts/i18n-check.ts` — it fails immediately (no baseline,
   no ratchet) if a literal English string ends up assigned to a
   `formError`/`message`/`fieldErrors` property or passed as a Zod
   `.min`/`.max`/`.regex`/`.email`/`.url` message argument anywhere under
   `src/app/**/actions.ts`, `src/lib/moderation`, `src/lib/validation`,
   `src/lib/push` or `src/config`.
5. `npm run typecheck && npm run test` — a test asserting the Turkish text
   under a `tr` request is the strongest guarantee a key actually resolves
   to what you intended; see `src/lib/validation/translate.test.ts`,
   `src/lib/push/messages.test.ts`/`send.test.ts`, and any `actions.test.ts`
   file using `__setMockLocale("tr")` (`src/test/next-intl-mock.ts`) for the
   pattern.
